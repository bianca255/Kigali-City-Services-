## Challenge 1: Firebase Authentication Email Verification

### Error Encountered
```
FirebaseAuthException (invalid-verification-code):
The SMS verification code used to create the phone auth credential is invalid.
```

**Context:**  
Initially attempted to implement both email and phone authentication. During testing, the email verification flow worked correctly, but when attempting to add phone authentication as an alternative, the verification code validation failed repeatedly.

### Root Cause
The error was misleading — it appeared to be a phone auth issue but was actually caused by misconfigured Firebase Authentication settings. The Firebase Console had SMS authentication enabled without proper reCAPTCHA configuration for the web platform, which caused cross-platform validation conflicts.

### Resolution Steps
1. Removed phone authentication implementation to focus on email/password exclusively
2. Verified Firebase Console → Authentication → Sign-in method: only Email/Password enabled
3. Ensured `firebase_auth` package version compatibility (5.7.0) with `firebase_core` (3.15.2)
4. Added proper error handling in `AuthService.signUp()`:
   ```dart
   try {
     final credential = await _auth.createUserWithEmailAndPassword(
       email: email,
       password: password,
     );
     await credential.user?.sendEmailVerification();
   } on FirebaseAuthException catch (e) {
     if (e.code == 'email-already-in-use') {
       throw 'An account already exists with this email.';
     }
     throw e.message ?? 'Authentication failed';
   }
   ```

### Lesson Learned
Firebase error messages can be misleading when multiple authentication methods are configured. Always verify Firebase Console settings match the code implementation, and enable only the authentication methods actively used in the application.

## Challenge 2: Firestore Security Rules and Permission Denied Errors

### Error Encountered
```
[cloud_firestore/permission-denied] The caller does not have permission
to execute the specified operation.
```

**Context:**  
After successfully implementing CRUD operations locally, deploying to Firebase resulted in permission-denied errors when attempting to create, update, or delete listings. Users could only read public listings but could not modify their own data.

### Root Cause
The default Firestore security rules generated by Firebase CLI were overly restrictive:
```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if false;  // Blocks all operations
    }
  }
}
```

Additionally, the initial rules did not properly verify user ownership before allowing updates or deletions.

### Resolution Steps

1. **Created user-specific access rules** (`firestore.rules`):
   ```javascript
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       // Users collection: users can only read/write their own profile
       match /users/{userId} {
         allow read, write: if request.auth != null && request.auth.uid == userId;
       }

       // Listings collection
       match /listings/{listingId} {
         // Anyone (authenticated) can read listings
         allow read: if request.auth != null;
         
         // Only authenticated users can create listings
         allow create: if request.auth != null 
                       && request.resource.data.createdBy == request.auth.uid;
         
         // Only the creator can update or delete their listings
         allow update, delete: if request.auth != null 
                                && resource.data.createdBy == request.auth.uid;
       }
     }
   }
   ```

2. **Deployed rules to Firebase**:
   ```bash
   firebase deploy --only firestore:rules
   ```

3. **Tested permissions in Firestore Console** using the Rules Simulator with different user UIDs to verify proper access control

### Lesson Learned
Security rules are the primary defense mechanism in Firebase applications. Server-side Firestore rules provide robust protection that cannot be bypassed by client-side code. Always test rules with the Firebase Console simulator before deployment to ensure they properly enforce access control while allowing legitimate operations.

## Challenge 3: Android Gradle Build Failures

### Error Encountered
```
FAILURE: Build failed with an exception.
* What went wrong:
A problem occurred configuring project ':app'.
> Could not resolve all artifacts for configuration ':app:debugRuntimeClasspath'.
  > Could not create task ':app:checkDebugAarMetadata'.
     > Installed Build Tools revision 33.0.0 is corrupted.
```

**Context:**  
After configuring Firebase and Google Maps dependencies, running `flutter build apk` resulted in Gradle build failures related to Android build tools version mismatches.

### Root Cause
The default Flutter Android configuration used outdated Gradle (8.4) and Android Gradle Plugin (AGP 8.2.0) versions. These versions were incompatible with the latest Firebase SDK dependencies which require AGP 8.9.1+.

### Resolution Steps

1. **Upgraded Gradle** (`android/gradle/wrapper/gradle-wrapper.properties`):
   ```properties
   distributionUrl=https\://services.gradle.org/distributions/gradle-8.13-all.zip
   ```

2. **Upgraded AGP and Kotlin** (`android/settings.gradle`):
   ```gradle
   plugins {
       id "com.android.application" version "8.9.1" apply false
       id "org.jetbrains.kotlin.android" version "2.3.0" apply false
   }
   ```

3. **Updated Java compatibility** (`android/app/build.gradle`):
   ```gradle
   compileOptions {
       sourceCompatibility JavaVersion.VERSION_11
       targetCompatibility JavaVersion.VERSION_11
   }
   kotlinOptions {
       jvmTarget = '11'
   }
   ```

4. **Cleaned build cache and rebuilt**:
   ```bash
   cd android
   .\gradlew clean
   cd ..
   flutter clean
   flutter pub get
   flutter build apk
   ```

### Lesson Learned
Firebase dependencies often require recent Android build tools. When integrating Firebase, always check the official [FlutterFire documentation](https://firebase.google.com/docs/flutter/setup) for minimum required versions of Gradle, AGP, and Kotlin, and upgrade proactively to avoid version conflicts.

## Additional Technical Insights

### State Management Architecture
Riverpod's `StreamProvider` proved ideal for real-time Firestore updates. By wrapping Firestore queries in streams, the UI automatically rebuilds when data changes:

```dart
final allListingsStreamProvider = StreamProvider<List<ListingModel>>((ref) {
  final service = ref.watch(listingServiceProvider);
  return service.streamListings();
});
```

This eliminated manual refresh logic and ensured data consistency across the Directory, My Listings, and Map View screens.

### Google Maps Integration
The `google_maps_flutter` package required platform-specific API key configuration. Critical gotcha: API keys must be restricted by bundle ID (Android) and bundle identifier (iOS) in the Google Cloud Console to prevent unauthorized usage.
