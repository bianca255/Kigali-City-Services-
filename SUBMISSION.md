## 1. Implementation Reflection

This project provided hands-on experience integrating Firebase Authentication and Cloud Firestore into a production-ready Flutter application. The integration required careful attention to platform-specific configuration, security rules, and state management patterns.

### Challenge 1: Firebase Authentication Email Verification

**Error Encountered:**
```
FirebaseAuthException (invalid-verification-code):
The SMS verification code used to create the phone auth credential is invalid.
```

**Context:**  
Initially attempted to implement both email and phone authentication. During testing, the email verification flow worked correctly, but when attempting to add phone authentication as an alternative, the verification code validation failed repeatedly.

**Root Cause:**  
The error was misleading — it appeared to be a phone auth issue but was actually caused by misconfigured Firebase Authentication settings. The Firebase Console had SMS authentication enabled without proper reCAPTCHA configuration for the web platform, which caused cross-platform validation conflicts.

**Resolution Steps:**
1. Removed phone authentication implementation to focus on email/password exclusively
2. Verified Firebase Console → Authentication → Sign-in method: only Email/Password enabled
3. Ensured `firebase_auth` package version compatibility (5.3.1) with `firebase_core` (3.6.0)
4. Added proper error handling in `AuthService.signUp()`
5. Configured Firebase Hosting for email verification links to work properly

**Lesson Learned:**  
Firebase error messages can be misleading when multiple authentication methods are configured. Always verify Firebase Console settings match the code implementation, and enable only the authentication methods actively used in the application.

### Challenge 2: Firestore Security Rules and Permission Denied Errors

**Error Encountered:**
```
[cloud_firestore/permission-denied] The caller does not have permission
to execute the specified operation.
```

**Context:**  
After successfully implementing CRUD operations locally, deploying to Firebase resulted in permission-denied errors when attempting to create, update, or delete listings. Users could only read public listings but could not modify their own data.

**Root Cause:**  
The default Firestore security rules generated by Firebase CLI were overly restrictive, blocking all operations. Additionally, the initial rules did not properly verify user ownership before allowing updates or deletions.

**Resolution Steps:**

1. Created user-specific access rules in `firestore.rules`
2. Implemented owner-only edit/delete permissions for listings
3. Added field validation to prevent invalid data
4. Tested rules using Firebase Console Rules Playground
5. Deployed updated rules using `firebase deploy --only firestore:rules`

**Lesson Learned:**  
Firestore security rules are critical for production applications. Always test rules thoroughly and implement the principle of least privilege. The Rules Playground in Firebase Console is invaluable for testing before deployment.

## 4. Design Summary

### Firestore Database Structure

**Collection: `users/`**
```javascript
{
  email: "string",              
  displayName: "string",        
  emailVerified: boolean,       
  createdAt: Timestamp,         
  notificationsEnabled: boolean 
}
```

**Collection: `listings/`**
```javascript
{
  name: "string",               
  category: "string",           
  address: "string",            
  contactNumber: "string",      
  description: "string",        
  location: {                   
    lat: number,                
    lng: number                 
  },
  createdBy: "string",          
  createdByName: "string",      
  createdAt: Timestamp,         
  updatedAt: Timestamp | null   
}
```

### State Management Architecture

**Riverpod Providers Used:**
- `authServiceProvider` - Singleton AuthService
- `firebaseAuthStreamProvider` - Raw Firebase auth state stream
- `userProfileProvider` - Full user profile with auth methods
- `listingServiceProvider` - Singleton ListingService
- `allListingsStreamProvider` - Live stream of all listings
- `myListingsStreamProvider` - Live stream filtered by user UID
- `filteredListingsProvider` - Search + category filter applied
- `searchQueryProvider` - Current search text
- `selectedCategoryProvider` - Active category chip
- `listingNotifierProvider` - Create/update/delete operations

### Key Design Decisions

1. **Service Layer Separation:** All Firebase operations isolated in `AuthService` and `ListingService`, never called directly from UI widgets

2. **Real-time Data Synchronization:** Used Firestore streams exposed through StreamProviders for automatic UI updates

3. **Owner-Based Access Control:** Listings can only be edited/deleted by their creator, enforced both in Firestore rules and UI logic

4. **Category Filtering:** Implemented as computed provider combining search and category state for optimal performance

5. **Error Handling:** Comprehensive try-catch blocks with user-friendly error messages in all async operations

### Technical Challenges Resolved

1. **Email Verification Links:** Configured Firebase Hosting to properly handle email action URLs
2. **Composite Indexes:** Created required Firestore index for efficient user-specific listing queries
3. **Map Integration:** Embedded Google Maps with proper API key configuration for Android/iOS
4. **State Management:** Ensured UI automatically rebuilds when Firestore data changes without manual refresh
